# Lab 01 — Lessons Learned

## 1. Overview

Lab 01 involved creating, testing and validating a PowerShell reporting solution that connects to Microsoft Graph, retrieves Microsoft Entra ID user and direct group membership information, and exports the results to a structured CSV report.

The exercise provided practical experience in PowerShell scripting, cloud identity administration, authentication, data validation, troubleshooting, reporting and technical documentation.

The main learning outcomes are recorded below.

## 2. PowerShell Development

### 2.1 PowerShell scripts should be designed for repeatability

A reusable script should not depend on hard-coded tenant identifiers, usernames or environment-specific paths.

Using parameters makes the script easier to reuse, test and maintain.

### 2.2 Parameter validation prevents avoidable errors

The `TenantId` parameter uses a regular-expression validation rule to reject incorrectly formatted GUID values.

A controlled negative test confirmed that malformed input is rejected before authentication.

This demonstrates the value of validating input at the earliest practical point.

### 2.3 Multiline PowerShell syntax requires care

During testing, a copied continuation prompt (`>>`) caused a parser error.

The issue demonstrated the importance of distinguishing actual PowerShell syntax from text displayed by the terminal.

It also reinforced the need to examine parser errors carefully rather than assuming the underlying cmdlet is defective.

### 2.4 PowerShell objects are preferable to manually formatted text

The script produces structured PowerShell objects before exporting them as CSV.

This allows data to be inspected, filtered, imported and processed consistently.

The use of `Import-Csv` demonstrated that the exported report remains usable as structured data.

## 3. Microsoft Graph and Entra ID

### 3.1 Microsoft Graph requires explicit authentication and permissions

Successful script execution depends on establishing an authenticated session with appropriate Microsoft Graph delegated permissions.

The lab demonstrated authentication using the device-code flow.

It also demonstrated that successful authentication and sufficient API permissions are related but distinct requirements.

### 3.2 Authentication context should be controlled

Using a process-scoped Microsoft Graph connection limits the persistence of the authentication context to the current PowerShell process.

The script also includes disconnection handling.

This supports better separation between lab sessions and reduces unnecessary persistence of authentication context.

### 3.3 Direct group memberships require interpretation

The script reports direct group memberships, not necessarily every group relationship visible through other administrative tools.

During validation, an existing organisation-wide Microsoft Team, `Modern Workplace Lab`, accounted for additional group memberships.

This demonstrated that apparently unexpected results may represent genuine underlying tenant configuration.

### 3.4 Source-system validation is essential

Results generated by a reporting script should be compared with the underlying administrative system.

The script's returned account and group information was reviewed against Microsoft Entra.

This provided stronger validation than relying solely on a successful terminal execution.

## 4. Reporting and Data Quality

### 4.1 Successful execution does not automatically prove report accuracy

A script may complete without an error while still producing incomplete or unexpected data.

The report therefore needs checks covering its existence, structure, record count and selected source-system values.

### 4.2 A zero result and a failed query are different

A user with no direct group memberships is not equivalent to a user whose group membership query failed.

The `MembershipQueryStatus` field helps distinguish these conditions.

The failure-reporting mechanism is implemented, although controlled failure-injection testing remains a possible improvement.

### 4.3 Timestamped reports improve traceability

Including a timestamp in the output filename and report content helps identify when a report was generated.

This supports comparison between reporting runs and provides an audit-friendly record of output generation.

### 4.4 Reporting scope must be documented

The script retrieves users according to the Microsoft Graph query performed, rather than restricting its output to the four manually created lab accounts.

This explains why the validated report contained eight user records.

Clearly documenting scope prevents readers from misinterpreting the results.

## 5. Troubleshooting and Testing

### 5.1 Controlled negative tests are valuable

Testing invalid input showed that the script rejects malformed Tenant IDs.

A robust solution should be evaluated against both expected and invalid input conditions.

### 5.2 Troubleshooting should follow evidence

The investigation of PowerShell syntax errors and additional group memberships reinforced a consistent approach:

1. Observe and record the unexpected behaviour.
2. Identify possible causes.
3. Test the most plausible explanations.
4. Compare findings with authoritative information.
5. Apply corrections where necessary.
6. Verify the result and document the outcome.

### 5.3 Tests must distinguish implementation from verification

The existence of validation or error-handling code does not automatically prove every possible failure scenario has been tested.

Test documentation should distinguish confirmed PASS results, FAIL results, and tests not yet performed.

## 6. Security and Privacy

### 6.1 Read-only operations reduce unnecessary risk

The reporting solution uses Microsoft Graph permissions intended for reading directory information.

It does not intentionally create, modify or delete Microsoft Entra users or groups.

### 6.2 Least privilege still matters for read-only operations

Read-only does not mean that data is non-sensitive.

Directory reporting can expose user identities, account status and group memberships.

Permissions, report storage and publication decisions therefore require consideration.

### 6.3 Credentials and authentication material must not be committed

Passwords, access tokens, refresh tokens, authentication codes and other secrets should never be included in a public GitHub repository.

Evidence screenshots must also be inspected for accidental exposure.

### 6.4 Generated reports should be separated from source code

Locally generated CSV reports are not automatically appropriate for public release.

The repository should primarily contain the script, documentation, testing evidence and any deliberately sanitised sample data.

## 7. GitHub and Documentation

### 7.1 Working code is only part of a complete engineering deliverable

A portfolio project is more useful when another person can understand its purpose, prerequisites, execution method, expected output, testing and limitations.

### 7.2 Documentation should reflect actual implementation

Claims about features, successful tests or security controls should correspond to functionality that exists and has been appropriately verified.

Documentation should not overstate the maturity of a learning project.

### 7.3 Separate documentation files improve maintainability

The repository uses separate files for the implementation guide, troubleshooting, lessons learned, script documentation and repository security policy.

This keeps technical information organised and reduces duplication.

### 7.4 Version control supports engineering traceability

GitHub provides a history of changes to published code and documentation.

Meaningful commit messages can help explain why a change was made and how the project developed.

## 8. Improvements Identified

Possible future enhancements include:

- Automated testing using Pester.
- A controlled test of failed group membership retrieval.
- A sanitised sample CSV containing synthetic identities.
- Configurable selection of users or groups.
- Additional report formats or automated validation checks.
- Better separation of reusable functions from the main script.
- Continuous integration to perform PowerShell static analysis and automated tests.

These are future improvements, not features claimed to be implemented in the current version.

## 9. Overall Reflection

Lab 01 strengthened my understanding of how PowerShell and Microsoft Graph can be used together for Microsoft Entra ID reporting.

Beyond writing a functional script, I practised investigating errors, validating output, interpreting directory data, identifying security considerations and documenting the complete implementation.

The most important lesson is that reliable IT engineering requires more than obtaining a successful result. It also requires understanding why the result is correct, how the solution behaves when something goes wrong, and how another person can safely reproduce and maintain it.
